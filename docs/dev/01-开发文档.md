### 2.1 后端需追加的 pom.xml 依赖

```xml
<!-- 数据访问层（主推方案）：MyBatis，注意 Spring Boot 4 必须用 mybatis-spring-boot-starter 4.x 系列 -->
<dependency>
    <groupId>org.mybatis.spring.boot</groupId>
    <artifactId>mybatis-spring-boot-starter</artifactId>
    <version>4.0.x</version>   <!-- 以 Maven 仓库中支持 Spring Boot 4 的最新版为准 -->
</dependency>
<dependency>
    <groupId>com.mysql</groupId>
    <artifactId>mysql-connector-j</artifactId>
</dependency>
<!-- JWT 认证（Auth0 版，API 简洁） -->
<dependency>
    <groupId>com.auth0</groupId>
    <artifactId>java-jwt</artifactId>
    <version>4.x</version>
</dependency>
<!-- 参数校验 -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>
```

**Spring Boot 4 注意事项**：
1. Starter 已模块化：Web 模块名为 `spring-boot-starter-webmvc`（工程中已有），数据访问模块为 `spring-boot-starter-jdbc`；
2. 若 MyBatis 4.x 与 Boot 4.1.1 出现兼容问题（启动报 Bean 相关错误），**降级为备用方案**：改用 `spring-boot-starter-jdbc` + JdbcTemplate（官方模块零兼容风险，调用存储过程用 `SimpleJdbcCall`，视图与普通 SQL 用 `JdbcTemplate` 直接写），仅替换数据访问层，其余分层不变。

### 4.1 数据库对象调用约定（本项目的核心约定）

| 数据库对象 | 后端调用方式 | 说明 |
| --- | --- | --- |
| 存储过程 | MyBatis：`<select statementType="CALLABLE">` 调用（或 SimpleJdbcCall） | 入社提交、角色变更、解散提交、建团执行、解散执行 5 个流程必须走 SP |
| 触发器 | **不调用**，只更新状态字段即可 | 入社审批：后端仅 `UPDATE join_apply` 置 agree（同时写 approve_stu_id、reply_time），`trg_join_apply_audit` 自动插入 club_member；角色写入时 `trg_club_member_role_*` 自动校验 1正2副 |
| 视图 | 查询直接 SELECT 视图 | v_club_info（社团概览）、v_join_apply_pending（审批台）、v_stu_club_record（学生档案）、v_club_member_detail（在职社员）；**更新只允许作用于单表字段**（如通过视图更新 join_apply 状态同样会触发触发器） |

## 5 身份认证与权限设计

### 5.1 登录与身份判定

1. **统一登录**：前端选择"学生/教师"身份（userType），后端按 userType 分别查询 `student` / `teacher` 表；密码为 SHA-256 哈希（前端加密后提交，后端直接比对哈希，不保存明文）；
2. **JWT 签发**：载荷含 `id`（学号/工号）、`name`、`userType`（student/teacher）；前端请求头 `Authorization: Bearer <token>`；后端拦截器解析后写入 UserContext；
3. **复合身份实时判定**（登录响应与 /api/auth/profile 中返回，前端据此渲染菜单）：
   - `unionMember`：`student_union_member` 存在该学号 → 学生会成员（可与社团身份叠加）；
   - `clubRole`：`club_member` 中 `leave_time IS NULL` 的在职记录（单社团制至多一条），role 为 president / vice_president / member；
   - 教师无叠加身份（teacher 表即全部）。

### 5.2 权限矩阵（后端接口校验依据）

| 接口域 | 普通学生 | 管理层（正/副） | 学生会 | 教师 |
| --- | --- | --- | --- | --- |
| 登录、社团浏览、系统消息查看 | ✓ | ✓ | ✓ | ✓ |
| 入社申请（本人） | ✓ | — | — | — |
| 建团提交（5 名无社团学生） | ✓ | — | — | — |
| 入社审批、踢出、晋升/降级/换届、活动申办与完结、社团公告管理、解散发起 | — | ✓ | — | — |
| 建团/解散审批（学生会侧）、学生会成员管理、系统消息发布 | — | — | ✓ | — |
| 建团/解散审批（教师侧）、活动审批、所辖社团数据 | — | — | — | ✓ |

**后端硬性校验点（评审决策 C4/C5/C6）**：
- C4：活动审批人必须是该社团绑定的指导教师（`club.tea_id` == 当前教师）；
- C5：移除学生会成员时须校验剩余成员数 ≥ 1；
- C6：学生会审批人（union 侧）必须 ∈ `student_union_member`；系统消息发布人同理；
- B4：管理层操作正副平权，仅"解散申请发起"限社长（SP 内已校验）；
- 所有权限校验失败统一返回 403。

## 6 核心业务流程的后端实现逻辑

> 每条流程标注：调用的 SP / 依赖的触发器 / 后端额外校验点 / 异常处理。

### 6.1 登录（学生/教师）
按 userType 查表 → 比对 SHA-256 → 签发 JWT → 返回 token + 身份信息（含 unionMember、clubRole）。

### 6.2 社团浏览
`SELECT * FROM v_club_info ORDER BY club_create_time DESC`（含指导教师姓名、在职社员数）。已解散社团因删除而不存在，天然不可见。

### 6.3 提交入社申请
`CALL sp_submit_join_apply(clubId, stuId)`。SP 内 SIGNAL 的业务提示（已入社 / 已有在途申请 / 社团解散冻结中）直接透传给前端；后端同时兜底捕获 `DuplicateKeyException`（1062）→ 提示"提交冲突"。

### 6.4 入社审批（管理层）
校验操作人为该社团在职管理层 → `UPDATE join_apply SET apply_status='agree'|'reject', approve_stu_id=当前操作人, reply_time=NOW() WHERE apply_id=? AND apply_status='pending'`。
- 同意后 `trg_join_apply_audit` 自动插入 `club_member`；
- 若学生已在他社（uk_stu_active 冲突，1062）→ 整个 UPDATE 回滚、申请保持 pending，后端捕获异常提示"该学生已加入其他社团，审批已回滚"。

### 6.5 主动退社（学生）
校验本人在社 → `UPDATE club_member SET leave_time=NOW(), leave_type='quit', operate_stu_id=本人 WHERE stu_id=? AND leave_time IS NULL`。留痕即闭环，无审批。

### 6.6 踢出社员（管理层）
校验：操作人管理层、目标为该社团在职社员且 `member_role <> 'president'`（社长不可被踢）→ `UPDATE ... SET leave_time=NOW(), leave_type='kick', operate_stu_id=操作人`。

### 6.7 晋升/降级/社长换届（管理层）
- **单人晋升/降级**：`CALL sp_change_member_role(clubId, targetStuId, newRole, operatorStuId)`（SP 内校验目标在职 + 操作人管理层；`trg_club_member_role_update` 校验 1正2副）；
- **换届（B5，专用接口 POST /api/clubs/{clubId}/change-president）**：前端一次提交"降级名单 + 新社长"，后端在同一个 `@Transactional` 内按序调用两次 SP——
  1. 原社长（及需调整的副社长）逐个降级为 member；
  2. 新社长晋升为 president。
  顺序不可颠倒（先升会被触发器拦截"已存在在职正社长"）；任一步失败整体回滚（原子换届，不产生"无社长"中间态）。

### 6.8 建团提交（5 名学生）
后端校验：5 名发起人均为不同学生且均无在社记录（查 club_member）、指定教师当前空闲（无 club 绑定，uk_tea_id 兜底）、社名不与现有社团冲突（uk_club_name 兜底）→ 事务内 `INSERT club_create_apply` + `INSERT club_create_apply_member`×5。

### 6.9 建团双审批（学生会 → 教师）
- **学生会侧**：`UPDATE club_create_apply SET union_audit_status='agree'|'reject', union_audit_stu_id=当前成员, union_audit_time=NOW()`；驳回时同时置 `final_status='fail'`；
- **教师侧**（指定教师本人）：`UPDATE ... SET tea_audit_status=..., tea_audit_time=NOW()`；
  - 驳回 → 置 `final_status='fail'`；
  - 同意且 union_audit_status='agree' → **`CALL sp_create_club(createApplyId)`**（SP 内部：双审校验 → 创建社团 → 5 发起人入社 1正2副2社员 → 置 final_status='success'）；
  - SP 抛错（发起人已入他社 / 社名被抢注 / 教师已被绑定）→ 整体回滚、申请保持 pending，后端透传具体原因，前端提示后人工处理。

### 6.10 活动申办（管理层）
校验：操作人管理层 + 该社团无 pending 解散申请（**B2 解散冻结**）→ `INSERT club_activity`（act_status 默认 wait_audit，apply_time 默认 NOW）。

### 6.11 活动审批（教师）
校验：当前教师 == 该社团 `club.tea_id`（**C4**）→ 同意置 `act_status='running'`（**B3**：开始/结束时间仅展示，不参与状态流转）；驳回置 `reject`；均写 `audit_tea_id`、`audit_time`。

### 6.12 活动完结（管理层）
`UPDATE club_activity SET act_status='finish' WHERE act_id=? AND act_status='running'`。

### 6.13 解散提交（社长）
`CALL sp_submit_dissolve_apply(clubId, stuId)`（SP 内校验：发起人在职社长 + 本社团无 pending 解散申请（**A3**））。

### 6.14 解散双审批（学生会 → 教师）
- 学生会侧：同 6.9，驳回置 `final_status='fail'`；
- 教师侧：驳回置 fail；同意且 union 已 agree → `UPDATE ... SET final_status='success'` 后 **`CALL sp_dissolve_club(dissolveApplyId)`**（SP 校验 success 后事务内按外键依赖顺序删除全部社团数据）。

### 6.15 社团公告管理（管理层）
发布/编辑：`INSERT` / `UPDATE`（title、content）；删除：`UPDATE ... SET is_deleted=1`（**C7 软删除**）；查询列表与详情一律过滤 `is_deleted=0`。

### 6.16 系统消息（学生会发布，全员可见）
- 发布/编辑：学生会成员 `INSERT` / `UPDATE`（publish_stu_id=当前成员，**C6 校验**）；
- 删除：软删除 `is_deleted=1`；
- 查看：全员（学生/管理层/学生会/教师）`SELECT ... WHERE is_deleted=0 ORDER BY publish_time DESC`。

### 6.17 学生会成员管理（学生会）
- 新增：`INSERT student_union_member` + `INSERT student_union_operate_log(operate_type='add')`；
- 移除：校验剩余成员 ≥ 1（**C5**，不满足则拒绝）→ `DELETE` + 操作日志（'remove'）。

## 7 异常处理与统一响应约定

### 7.1 统一响应结构

```json
{ "code": 0, "message": "success", "data": { } }
```

| code | 含义 | 触发场景 |
| --- | --- | --- |
| 0 | 成功 | — |
| 400 | 参数错误 | @Validated 校验失败 |
| 401 | 未登录 / token 失效 | 拦截器 |
| 403 | 无权限 | 权限矩阵校验失败 |
| 404 | 资源不存在 | 记录不存在 |
| 1001 | 业务校验失败 | SP 内 SIGNAL 的 MESSAGE_TEXT **原样透传**（如"您已有待审批的入社申请"） |
| 1002 | 数据冲突 | DuplicateKeyException（1062，唯一键冲突） |
| 500 | 服务器错误 | 兜底异常 |

### 7.2 全局异常处理器（@RestControllerAdvice）规则
1. `BizException` → 1001，message 原样透传；
2. `DuplicateKeyException` → 1002，"数据冲突，请刷新后重试"；
3. `MethodArgumentNotValidException` → 400，取第一条校验消息；
4. 其余 → 500，message 不泄露内部细节（打印日志即可）。

## 9 编码规范（约定）

1. **包名**：沿用 `com.simplet1me.database.*`；Controller 类名 `XxxController`，Service `XxxService` + `impl/XxxServiceImpl`；
2. **DTO**：请求类 `XxxReq`，响应类 `XxxVO`；entity 与表字段驼峰映射；
3. **时间**：全项目 `yyyy-MM-dd HH:mm:ss`，Jackson 全局配置；
4. **权限**：一律在 Service 层显式校验（拦截器只负责登录态），禁止在 Controller 里散落 if；
5. **事务**：多步写操作必须 `@Transactional`（特别是换届两步、建团明细+主表）；
6. **异常**：业务失败抛 `BizException`，不吞异常；SP 的 SIGNAL 错误必须透传到前端；
7. **SQL**：全部参数化（#{} 或 ?），禁止字符串拼接；查询优先用视图。
