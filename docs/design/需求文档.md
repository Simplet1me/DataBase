# 学生社团管理系统 - 详细需求规格说明书（闭环完整版）

## 1 引言

### 1.1 项目背景

传统高校学生社团管理依赖人工统计、线下审批、纸质登记，存在社团创建流程混乱、社员管理不规范、活动审批低效、社团解散无流程、权限划分模糊、数据无法追溯等问题。为实现高校学生社团信息化、规范化、流程化管理，搭建本学生社团管理系统。系统覆盖学生入社、社团创建、社团解散、社员权限管理、社团活动申办、学生会审批、教师审批、公告发布、日志追溯等全流程业务，实现社团管理全生命周期闭环。

### 1.2 文档目的

本文档为学生社团管理系统完整需求规格说明书，明确系统整体业务规则、角色权限、功能性需求、非功能性需求、业务流程、数据约束、异常处理机制，作为数据库设计、系统开发、课程设计验收的唯一依据，所有需求均可通过现有数据库结构实现，业务完全闭环无漏洞。

### 1.3 运行环境

- 数据库：MySQL 5.7 / 8.0
- 开发架构：B/S 架构（Web端）
- 运行环境：Windows / Linux

## 2 系统整体概述

### 2.1 核心业务目标

实现高校学生社团从申请创建、正式运营、社员管理、活动开展、公告发布、解散注销的全生命周期信息化管理，区分普通学生、社团管理层、学生会管理部门、指导教师四大角色，权责分离、流程规范、数据可追溯、业务可闭环。

### 2.2 系统角色划分（四大核心角色）

系统所有用户分为四类角色，角色权限完全隔离，无越权操作：

| 角色 | 核心职责 |
| --- | --- |
| 普通学生 | 浏览社团、提交入社申请、主动退社、参与活动、发起建团申请、查看系统消息 |
| 社团管理层（正社长、副社长） | 社员管理、入社申请审批、社团活动申办、公告发布、发起社团解散申请、社员晋升降级 |
| 学生会管理部门成员 | 平权管理，审批社团创建申请、审批社团解散申请、维护学生会成员、查看审批日志、发布系统消息 |
| 指导教师 | 绑定指导社团、审批社团创建、审批社团解散、审批社团活动、查看所辖社团数据 |

> 注：学生会成员身份与社团社员/管理层身份互不冲突，可同时兼任。

## 3 整体业务约束（全局硬性规则）

所有约束均对应数据库结构或代码逻辑，全程闭环生效：

| 序号 | 约束名称 | 约束内容 | 落实方式 |
| --- | --- | --- | --- |
| 1 | 教师唯一约束 | 一名指导教师同一时间只能指导一个社团 | 数据库硬约束：club 表 `uk_tea_id` 唯一索引 |
| 2 | 学生单社团归属约束 | 一名学生同一时间只能加入一个社团 | 数据库硬约束：club_member 表 `uk_stu_active` 唯一索引（生成列） |
| 3 | 社团角色数量约束 | 单个社团仅允许 1名正社长、最多2名副社长，其余均为普通社员 | 数据库触发器硬校验：trg_club_member_role_insert / trg_club_member_role_update（角色写入与变更前校验） |
| 4 | 建团人数约束 | 新建社团必须由5名无任何社团归属的学生共同发起 | 业务代码软约束：提交时校验发起人数量与社团归属（club_create_apply_member 记录发起人） |
| 5 | 双审批约束 | 社团创建、社团解散必须同时通过【学生会部门审批 + 指导教师审批】方可生效 | 数据库状态字段 + 代码事务：union_audit_status / tea_audit_status / final_status |
| 6 | 活动审批约束 | 社团活动仅由所属指导教师单独审批，无需学生会介入 | 数据结构保证：club_activity 仅设 audit_tea_id 教师审批字段 |
| 7 | 学生会平权约束 | 所有学生会成员权限一致，无上下级区分，均可审批社团创建/解散申请 | 数据模型保证：student_union_member 无层级字段 |
| 8 | 退社类型约束 | 学生退社分为两种：主动退社、社长踢出，全程留痕（记录退社时间、类型、操作人）；社团解散时社员记录随社团整体删除，不单独留痕 | 数据库字段留痕：club_member.leave_time / leave_type / operate_stu_id（kick踢出 / quit主动退社） |
| 9 | 申请防重复约束 | 同一学生同一时间只能有一个待审批入社申请（不可同时向多个社团提交） | 存储过程校验：sp_submit_join_apply 提交前校验任意 pending 记录 |
| 10 | 数据完整性约束 | 除社团解散流程外，所有删除操作采用外键限制，禁止删除关联业务数据，保证数据安全 | 数据库硬约束：外键 ON DELETE RESTRICT |
| 11 | 账号预置约束 | 学生、教师账号由系统预置/批量导入，不开放自主注册 | 系统初始化约定 |
| 12 | 解散冻结约束 | 社团解散申请待审批期间，该社团暂停入社申请与活动申办 | 存储过程/后端校验：sp_submit_join_apply 校验入社申请；活动申办由后端校验 |

## 4 详细功能性需求（全闭环）

### 4.1 普通学生功能需求

1. 个人信息管理：查看个人学号、姓名、班级、联系方式，支持修改登录密码。
2. 社团浏览：查看所有正常运营的社团列表、社团简介、社团公告；社团解散后其数据即被系统删除，不可浏览和申请加入。
3. 入社申请管理：选择社团提交入社申请；实时查看申请状态（待审批、同意、拒绝）。
4. 创建社团申请：无社团归属的学生，可联合其余4名无社团学生发起建团申请；填写社团名称、简介、选择指导教师；可实时查看学生会、教师双审批进度。
5. 主动退社功能：已入社学生可自主申请退社，无需管理员审批，退社数据留痕，记录退社类型与时间。
6. 活动参与：浏览本社团已审批通过的活动，参与活动开展。
7. 系统消息查看：查看学生会发布的全员消息。
8. 个人社团记录查询：查看当前所属社团、社团角色、历史入退社记录、角色变更记录。

### 4.2 社团管理层（正/副社长）功能需求

正社长与副社长权限一致（仅 4.2.6 社团解散申请限社长发起）：

1. 社员信息管理：查看本社团全部在职社员、社员角色、入社时间、历史退社记录。
2. 社员权限管理：
   - 社员踢出：可强制踢出普通社员、副社长，系统记录踢出类型、操作人（operate_stu_id）与操作日志。
   - 社员晋升/降级：可对普通社员晋升副社长、对副社长降级为普通社员；严格遵守1正2副人数限制；所有角色变更自动写入变更日志，永久追溯。
   - 社长换届：由人工指定新社长；操作顺序须先将原社长及需调整的副社长降级为普通社员，再晋升新社长（1正2副触发器校验，先升将被拦截）；所有角色变更自动写入变更日志。
3. 入社申请审批：查看本社团所有待审批入社申请；支持同意/拒绝操作；记录审批人与审批时间。
4. 社团活动管理：填写活动信息、提交活动申办申请至指导教师；查看活动审批状态、活动进度；活动结束后更新活动状态。
5. 社团公告管理：发布、查看、编辑、删除本社团公告（删除为软删除，保留发布记录），记录发布人、发布时间。
6. 社团解散申请：仅社团社长可发起社团解散申请；提交后等待学生会与指导教师双审批；可实时查看审批进度与结果。

### 4.3 学生会管理部门功能需求

学生会全体成员平权，无权限差异，所有成员拥有同等审批与管理权限：

1. 社团创建审批：查看所有待审核的新建社团申请；支持同意/驳回操作；记录审批人、审批时间。
2. 社团解散审批：查看所有待审核的社团解散申请；支持同意/驳回操作；记录审批人、审批时间。
3. 学生会成员管理：支持新增学生会成员、移除现有成员（须至少保留一名成员，后端校验）；所有成员变动自动生成操作日志，永久留存。
4. 审批记录查询：可查看所有历史建团审批记录，数据可追溯；社团解散时解散审批记录随社团数据一并删除，不保留。
5. 系统消息发布：编辑消息标题与内容并发布；支持编辑与删除已发布消息（删除为软删除）；消息面向全体用户（普通学生、社团管理层、指导教师）可见；记录发布人与发布时间，可查看历史发布记录。

### 4.4 指导教师功能需求

1. 社团创建审批：接收学生建团申请，审核通过或驳回；仅未绑定社团的教师可被选为指导教师。
2. 社团解散审批：审核自己所指导社团的解散申请，完成审批操作。
3. 社团活动审批：审核所辖社团提交的所有活动申办申请（仅该社团绑定的指导教师可审批，后端校验），同意则活动生效，驳回则终止申办。
4. 社团数据查看：查看自己指导社团的基本信息、社员名单、活动记录、公告信息。
5. 系统消息查看：查看学生会发布的全员消息。

## 5 核心业务闭环流程（完整闭环无断点）

### 5.1 新社团创建闭环流程

5名无社团学生发起建团申请 → 绑定指定空闲指导教师 → 生成建团申请记录 → 学生会成员审批 → 指导教师审批 → 双同意则创建社团成功 → 自动将5名发起人录入社员表 → 自动分配1正社长、2副社长、2普通社员 → 生成社团初始数据。

任意一方驳回，则建团失败，流程终止，记录驳回状态。

### 5.2 学生入社闭环流程

学生提交入社申请 → 社团正/副社长查看申请 → 同意：自动新增社员记录 → 流程结束；拒绝：更新申请状态 → 流程结束。

### 5.3 社员退社闭环流程

- 主动退社：学生自主退社 → 系统自动记录退社时间、退社类型 → 终止社员权限 → 流程闭环。
- 社长踢出：管理员踢出社员 → 记录踢出时间、类型、操作人 → 权限终止 → 流程闭环。
- 社团解散：双审批通过解散社团 → 删除社团及全部关联数据（含全部社员记录，不单独留退社记录）→ 社员恢复无社团归属、管理层职位与指导教师绑定同步释放 → 流程闭环。

### 5.4 社团活动申办闭环流程

社团社长/副社长提交活动申办 → 指导教师接收审批 → 通过：活动状态置 running（活动开始/结束时间仅作展示）→ 活动结束手动完结；驳回：活动终止 → 全程状态留痕。

### 5.5 社团解散闭环流程

社团社长发起解散申请 → 学生会审批 → 指导教师审批 → 双同意：事务内删除该社团全部关联数据（入社申请、活动、公告、角色变更日志、解散申请、社员记录）后删除社团 → 全体社员恢复无社团归属、管理层职位释放、指导教师恢复空闲 → 流程闭环；任意驳回则解散失败。

## 6 非功能性需求

### 6.1 数据完整性

所有业务操作均留存记录，禁止物理删除核心业务数据；仅社团解散流程经双审批通过后允许整体删除社团及其关联数据，保证数据可追溯、流程可复盘。

### 6.2 权限安全性

角色权限严格隔离，学生无法审批申请、普通社员无法管理社员、学生会无法管理社团内部业务、教师无法干预学生会审批。用户密码采用 SHA-256 哈希存储（由应用层加密后入库，数据库不保存明文密码）。

### 6.3 易用性

界面操作简洁，流程清晰，所有操作结果实时反馈，审批进展通过各申请的状态字段查询。

### 6.4 可维护性

所有业务变更、人员变动、权限变更均留存日志，便于后期维护与问题排查。

## 7 需求闭环验证说明

本文档所有需求100%适配当前数据库结构，无超范围需求、无缺失需求、无逻辑冲突需求：

- 所有业务流程均可通过现有14张数据表完整落地（student、teacher、student_union_member、student_union_operate_log、club、club_member、club_member_change_log、join_apply、club_create_apply、club_create_apply_member、club_dissolve_apply、club_activity、club_notice、system_message）；
- 所有约束分为数据库硬约束 + 业务代码软约束，分工明确；
- 所有操作均可形成发起-审批-执行-留痕完整闭环；
- 无业务漏洞、无逻辑死循环、无功能断点，完全满足数据库课程设计验收标准。
